# OpenTabletDriver patches

`external/OpenTabletDriver` is OpenTabletDriver v0.6.8-rc1 (upstream commit 126f482, LGPL-3.0), vendored with the patches below already applied, so a plain clone builds the same app.

- `otd-macos-f13-f15.patch`: adds F13, F14 and F15 to the macOS virtual keyboard (needed for Photoshop's Option+F13 / Option+F14 rotation).
- `otd-daemon-quiet-closed-rpc.patch`: the daemon logs a client closing its JSON-RPC connection ("Cannot access a disposed object ... StreamJsonRpc.JsonRpc") at debug level instead of as an error.

## otd-pth651-wireless-receiver.patch

Discussion #31 (best attempt, untested): adds the Wacom Wireless Receiver (ACK-40401, USB 056a:0084, product ID 132) to `Wacom/PTH-651.json`, re-using the USB parsers. Source: Linux `drivers/hid/wacom_wac.c` (`wacom_features_0x84`, "Wacom Wireless Receiver"). Apply from inside `external/OpenTabletDriver` with `git apply`.

- `otd-macos-double-click.patch`: Version 25 tip double-click. Hover between taps no longer breaks the click count; only a drag while held does. Adds Tip Double Click Distance (default 40 px), `IMouseDoubleClickHandler`, and a Double Click binding that posts left down/up click-count 1 then 2.
- `otd-macos-edge-activation.patch` (apply after the double-click patch): Version 25. In absolute mode the macOS pointer is kept 1/64 px inside the display it is on, so the Dock and hot corners trigger at the edge (OTD #4726). Before a left mouse-down, the app that owns the window under the pointer is activated (macOS 27 raises the window but doesn't activate it; desktop → Finder). A Window Server window that covers the display is skipped (#73). Notification Center windows that cover the whole display are skipped so a tap falls through to the app below; banners, the open panel and widgets are kept (Kert Gartner, V25). Fails open.
- `otd-macos-relative-clicks.patch` (apply after the edge-activation patch): Version 26 (#36, Maxime; also #73). Relative (Mouse-like) mode fed pointer movement to the double-click counter, so every click within the double-click time counted as a double, triple… click and a drag never broke the count; it now counts at screen points (pointer + movement). And every settings change (for example a per-app switch caused by the click itself) built a new virtual mouse without letting go of a button the old one held, leaving macOS with a left button down that no one released; the daemon now posts the ups, where the pointer is, before it drops the old mouse. Fails open. Best attempt, untested on a Mac.
- `otd-feature-report-sequence.patch` (apply after the relative-clicks patch): Version 26 (#7 / #18, Brice, Intuos4 OLED key labels). New daemon call `SendFeatureSequence(vid, pid, interface, reports)`: several feature reports in order through ONE open device stream (HidSharp starts two threads per stream on macOS, so one stream per report is wasteful for the 48 reports that fill eight key screens), to every matching tablet. A report longer than the device's declared feature report length (HidSharp would cut it short) goes straight through IOKit `IOHIDDeviceSetReport` on macOS (`MacHidFeature.cs`); elsewhere it is refused with a log line. Fails open. Best attempt, untested on an Intuos4 with screens.

- `otd-radial-default-button2.patch` (TASKS #56, Zak 17:12): a new tablet profile (fresh install, a newly detected tablet, the daemon's ResetSettings) starts with pen button 2 set to the app's Radial menu (`OpenTabletArtist.Dynamics.RadialMenuBinding`, no Menu setting = the default menu) and the matching `RadialMenuFilter` in the profile's filters. Button 1 and the others keep OTD's defaults. The daemon only stores the plugin type names; the app ships the plugin. Already applied in `external/OpenTabletDriver`.

- `otd-held-button-release.patch` (apply after the radial patch; TASKS #3 part 3, issue #73, Maxime): a virtual mouse button that macOS was told is down and never told is up makes the user's real mouse button useless (the real left button stops clicking, right-click still works). The pointer is now dropped without letting go in three more ways than a settings change: the tablet is unplugged or re-detected (`Driver` disposes the output mode), the driver is told to stop (the daemon posts the ups before it exits), and the app stops the driver by killing it (the app now sends SIGTERM first, see `GracefulProcessStop`). Also: `Reset()` (pen leaves range) lets go of what was *posted*, not what was *requested*, and a pen-button Double Click is skipped while the pen holds the left button (its four raw events bypassed the held-button bookkeeping). New `IHeldButtonReleaser` / `HeldButtonRelease.TryRelease` (never throws, logs every outcome). Best attempt, untested on a Mac.

- `otd-sigterm-release.patch` (apply after the held-button patch; Version 27, review of #107): the daemon now handles SIGTERM itself. `otd-held-button-release.patch` relied on .NET running the `AssemblyLoadContext.Unloading` handler on SIGTERM, but it doesn't: a test process with the daemon's exact shutdown shape (console in use, SIGHUP registration, Unloading handler that cancels and waits) was simply terminated (exit 143) and its clean-up never ran, so the app's polite stop did NOT let go of a held button. With a `PosixSignalRegistration` for SIGTERM (Cancel = true, then the same CloseDaemon) the clean-up runs and the process exits 0. Checked on Linux with .NET 10; the signal code is the same on macOS. Already applied in `external/OpenTabletDriver`.

- `otd-already-running-exit-code.patch` (apply after the SIGTERM patch; Version 28, TASKS #74): when another driver already holds the "only one driver" lock, the daemon now exits with code 3 instead of 0, so the app can say "another driver is already running" instead of "an incomplete install" (the app's `DriverProcessFinder.AlreadyRunningExitCode`). The daemon also logs, at start, its process id, its parent's and its own path, and logs a stop by SIGHUP at Write level, so a driver left behind by another copy of the app can be traced. Already applied in `external/OpenTabletDriver`.

- `otd-bamboo-pt-touch.patch` (apply after the exit-code patch; Version 28, TASKS #77, Daniel's CTH-461; plan agreed by Claude and Devin): on a Bamboo Pen & Touch (CTH-460, CTH-461, CTH-661: Linux type BAMBOO_PT, `touch_max` 2) the 20-byte report 0x02 carries the four ExpressKeys AND up to two fingers. `BambooV2AuxReportParser` read it as an Intuos aux report, whose touch-ring bytes are this report's finger bytes, so a finger could send false ring and ring-button events. It now returns `BambooV2TouchReport`: keys from data[1] bits 0-3 and up to two touch points, no wheel. Format from Linux `drivers/hid/wacom_wac.c` (`wacom_bpt_touch`). The three configs get a Touch size (the pen area; MaxX/MaxY 1023, the kernel's default when the HID descriptor gives none: to confirm from a user's Record the problem). The app's Touch trackpad (Beta) uses it; these models start with touch OFF. Best attempt, untested on the hardware. Already applied in `external/OpenTabletDriver`.

- `otd-gettablets-snapshot.patch` (apply after the Bamboo touch patch; Version 28, TASKS #80; plan agreed by Claude and Devin): `Driver.Tablets`, the `TabletsChanged` event on a disconnect, and `InputDeviceTree.CreateReference` now hand out finished arrays instead of lazy queries, so JSON-RPC, which enumerates the result later on its own thread, never walks a device list that detection is changing. A guard of the same kind as the next patch; it was NOT the cause of Daniel's error (that was GetDevices, see below). Already applied in `external/OpenTabletDriver`.
- `otd-getdevices-snapshot.patch` (apply after `otd-gettablets-snapshot.patch`; Version 28, TASKS #80; PROVEN by Daniel's report of 15 Nov): his app.log at 12:38:48.909 says the app's `GetDevices` call failed with 'Error writing JSON RPC Message: InvalidOperationException: Collection was modified', and his driver log shows a device being added at that moment (12:38:48.876 and .897). `RootHub.GetDevices` returned its live endpoint list and `DriverDaemon.GetDevices` wrapped it in a lazy `Select`, so JSON-RPC wrote it out while the device change was rewriting it. Now `RootHub` copies the list under its lock (also when it builds the change event and re-enumerates), and `DriverDaemon.GetDevices` returns an array. Upstream master (2b29caa, 15 Nov 2026) still has the live list. Test: `TabletListSnapshotTests.TheDeviceList_CanBeReadToTheEnd_WhenATabletIsPluggedInWhileItIsBeingRead` (fails with Daniel's exact exception without the patch). Already applied in `external/OpenTabletDriver`.
- `otd-macos-activation-worker.patch` (apply after `otd-getdevices-snapshot.patch`; Version 28, TASKS #85; PROVEN by mtr8080's report of 16 Nov, Intuos5 PTH-650, macOS 27.2.1): a pen click on another app's window brought that app forward only after about 1 s. `MacOSAppActivator` called `activateWithOptions:` on the input thread before posting the left mouse-down, and on his Mac that call took about 1 s for every app it brought forward: in his 5 driver logs the next gated tap after "Activated X" lasted 1004-1042 ms in 108 of 108 clicks, against a median of 81 ms (max 254) in 121 clicks on an app that was already active. The activation now runs on one dedicated background thread (`SingleSlotWorker`: one job at a time, a request while one is running is dropped, an exception doesn't stop the thread); the click waits for it at most `MacOSAppActivator.ClickWaitMs` (50 ms), so a quick activation still comes before the click as in V25-V27. Logs "Activated X in N ms." and, when the wait runs out, "Posted the click after 50 ms; activation of X still running." Tests: `SingleSlotWorkerTests`. Best attempt, untested on a Mac. Already applied in `external/OpenTabletDriver`.
- `otd-macos-cursor-window-pick.patch` (apply after `otd-macos-activation-worker.patch`; Version 28 or 29, TASKS #85, Claude decides): in Zak's V28 one-click test of 16 Nov every pen tap (7 of 7) picked "Window Server layer 2147483630 size 55x78" at the pen position, so no app was activated and the #85 worker never ran; mtr8080's logs show the same pick 51 times. On those Macs the pointer is a real cursor-layer Window Server window. `MacOSWindowPick.Pick` now skips a Window Server window at `CursorLayer` (2147483630) or above that is at most `MaxCursorSide` (256) on each side, and looks behind it; the menu bar (layer 24) and display-sized shields keep their #73 rules. Tests: `MacOSEdgeAndActivationTests` (`A_cursor_window_under_the_pen_is_skipped_v28_85`, `A_large_or_lower_Window_Server_window_is_not_taken_for_the_cursor_v28_85`). Best attempt, untested on a Mac. Already applied in `external/OpenTabletDriver`.
